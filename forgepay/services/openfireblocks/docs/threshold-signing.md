# Threshold signing (t+1 of n)

Each workspace gets its own secp256k1 key, generated by distributed key generation
(bnb-chain/tss-lib) across the signing nodes. No node, and not the coordinator, ever holds the
whole key. Any `t+1` nodes sign together; the signature is ordinary ECDSA and verifies as the
workspace's address on-chain.

## Components
- `mpc-signer` — the coordinator. Holds only an ed25519 key used to sign session requests. Keeps no
  key registry: what a key's committee and epoch are is read from the nodes.
- `mpc-node` — one per share. Peer-to-peer encrypted messages, sealed share at rest, its own
  signing policy, hash-chained audit log (`mpc-node verify-audit`).
- api-gateway — creates a key the first time a workspace needs one, and can provision every existing
  workspace at once (`custody.keys`).

## Where each protection comes from
| Concern | Mechanism | Verified by |
|---|---|---|
| A stolen node disk | Everything on disk is AES-GCM sealed. The seal key is wrapped by **Vault transit or AWS KMS**, bound to the node id; `MPC_ENV=production` refuses `file`/`env` seal keys. | `sealprovider_test.go` (fake Vault, fake KMS), plus a real Vault dev server: init, migrate, rewrap, wrong token, Vault down |
| One place holding enough shares | Cluster file declares each node's **trust domain**. Production refuses a topology in which any one domain holds `t+1` nodes, for keygen, reshare and start-up. | `topology_test.go` |
| Eavesdropping, stray callers | **Mutual TLS** with a shared private CA. A node's certificate name is its id: only the coordinator's may start ceremonies, and a peer may only send messages as itself. Renewed certificates are picked up without a restart. | `TestMutualTLSIdentifiesCallers` |
| A compromised gateway or coordinator asking for too much | Each node's **own policy** (below), applied to the transaction the node rebuilt itself. | `TestThresholdSigningAcrossRealNodes` policy subtest, `policy_test.go` |
| A share that leaks later | **Resharing**: a key moves to fresh shares, a different committee or a different threshold, keeping its address. Old shares are destroyed. | `TestReshareMovesAKeyWithoutChangingItsAddress` |

## Node policy
A JSON file on the node's own host (`MPC_NODE_POLICY_FILE`, or `-policy`), reloaded when edited. The
coordinator cannot change it. A file that no longer parses keeps the previous rules in force.

| Rule | Meaning |
|---|---|
| `maxValueWei` | cap on one transaction's value |
| `maxFeeWei` | cap on gas limit × the highest per-gas fee offered |
| `dailyLimitWei` | rolling 24h total this node will co-sign, per key (persisted; released if the ceremony fails) |
| `maxTxPerHour` | rolling hour count, per key |
| `allowedChainIds` | networks this node signs for |
| `allowedDestinations` / `blockedDestinations` | recipient allowlist / blocklist; the blocklist also checks the recipient inside a standard token `transfer`/`approve`/`transferFrom` |
| `allowCalldata: false` | plain value transfers only |
| `allowedSelectors` | permitted contract functions |

The node reports a digest and the list of active rules on `/v1/health`; the console shows them.
Reservations against the rolling limits are conservative across a crash: a ceremony interrupted by a
crash stays counted until it ages out of the window.

## Production topology
1. **One node per trust domain.** For a 2-of-3 key: three nodes, each in a different account/host/
   operator, no two under one administrator. The domain label in `cluster.json` is a *declaration* —
   the software can refuse a topology that visibly puts everything in one domain, but cannot prove a
   label is true. Make it true.
2. **PKI.** `mpc-node pki-init -dir ca` once, kept by whoever the operators agree on;
   `mpc-node pki-issue -ca ca -name node1 -hosts node1.example -out node1-tls` per node and
   `-name coordinator` for the signer. Nodes need only `ca.pem` and their own cert/key.
3. **Seal key.** Create a transit key per node and give the node an AppRole that can use only that key
   (`deploy/mpc/vault-policy.example.hcl`). `mpc-node init` with `MPC_SEAL_PROVIDER=vault` writes
   `seal.key.wrapped`; the plaintext key never touches disk. For an existing dev node:
   `mpc-node seal-migrate -id node1 -data DIR -from file -to vault`. After a Vault key rotation,
   `mpc-node seal-rewrap`. The key service is needed at start-up, not while signing.
4. **Policy.** Write `policy.json` on each node's host (`deploy/mpc/policy.example.json`).
5. **Check the key service for real.** `mpc-node seal-check -provider vault|awskms` wraps and unwraps a throwaway key against the
   actual Vault or KMS and confirms it won't load for another node and that a tampered file is refused. `deploy/aws/kms-policy.example.json`
   is a least-privilege IAM policy for the KMS case.
6. **Check.** `mpc-node preflight -id node1 -data DIR -cluster cluster.json` prints what production
   start-up would refuse and what it merely dislikes. Exit status is non-zero on failure.
7. Run with `MPC_ENV=production` (`deploy/mpc/node.env.example`, `Dockerfile.node`).

`scripts/mpc-dev-cluster.sh` can exercise the same paths locally: `MPC_DEV_TLS=1`, `MPC_DEV_SEAL=vault`.

## Rotation and resharing
A key moves to a new committee and/or threshold **without changing its public key or address**, so funds
do not move. Every party's identity is tied to a key **epoch** (0 as generated, +1 per reshare).

**Who can ask.**
- A workspace's own signers, as a governance proposal (`rotate_key`, payload `{nodes, signers_needed}`),
  approved by the same quorum as any other governance change. The console offers it on the Keys page.
  If carrying it out fails (say a node is down) the proposal shows *approved · not carried out* with the
  reason, and **Retry** runs it again without new votes.
- The platform operator, for every workspace at once (for example after replacing a node):
  `POST /admin/custody/keys/rotate-all {"nodes":[...],"signersNeeded":2}` runs in the background, one
  workspace at a time; `GET /admin/custody/keys/rotate-all` reports progress and per-workspace failures.
  Workspaces already on that committee are skipped.

**Order of operations**, chosen so a failure at any step leaves the key usable as before:
1. the old committee (`t+1` current holders) and the new committee run resharing; new members store a *pending* share;
2. every new share is checked to reproduce the original public key;
3. the new committee signs a throwaway, domain-separated digest (never a transaction hash);
4. pending shares are committed; then
5. old shares are overwritten and removed.

Steps 1-3 failing discards the pending shares. A node that was offline at step 5 is listed as still
holding a retired share (the result's `not_retired`, and `stale_nodes` on the Keys page); **Destroy old
shares** (or `POST /mpc/keys/{id}/retire-stale` on the signer) finishes the job when it returns.

**Limits of what it needs.** Every *new* member must be online (it receives a share), and `t+1` of the *old*
holders must be online (they contribute theirs). A 3-of-3 key therefore cannot be re-split while a node is
down. A new member also needs a spare pre-parameter set, which is CPU-bound to make: the reshare says so and
can be retried, rather than waiting.

**What resharing does and does not protect against.** The key itself does not change, only how it is split.
An attacker who collected *fewer than `t+1`* old shares before a reshare is left holding pieces that no longer
combine with anything: that is what rotation buys (replace a node you suspect, refresh on a schedule so shares
stolen over time never add up). An attacker who already holds `t+1` old shares can rebuild the key, and
resharing does not undo that: the answer then is a new key and moving funds to it. Retire stale shares
promptly so honest nodes never hold a usable old share.

Nodes can be added or moved by editing `cluster.json`; running processes re-read it when it changes.
The coordinator key and existing nodes' identity keys cannot change that way.

## Trust secrets between the console, gateway and signer

Three secrets, kept in one Secret (`custodySecretsRef` in the Helm chart), none in the repository:

| Variable | Held by | What it does |
|---|---|---|
| `MPC_SIGNER_AUTH_TOKEN` (>= 32 chars) | signer, api-gateway, temporal-worker | Bearer token every signer route except `/health` requires. Production refuses to start without it. |
| `CUSTODY_ACTOR_SECRET` | console, api-gateway | The console signs each custody request (actor, method, path, body hash, timestamp, nonce); the gateway verifies, so the shared admin key alone cannot cast a signer's vote. |
| `CUSTODY_PROPOSAL_SECRET` | api-gateway | Seals each proposal's payload so an edit in the database after the votes is refused at execution. |

Also: `MPC_REQUIRED=true` (production requires it; the legacy shared key is never loaded), a node policy with at least one rule
(production requires it), `API_KEY_AUTO_SIGN_MAX_WEI` or `policies.apiKeyAutoSignMaxWei` (API-key transfers above it wait for a
quorum; the default in production is 0 = all of them), and optionally per-token caps in the node policy (`maxTokenUnits`,
`dailyTokenUnits`, `requireTokenCaps`). Limits of this design are listed in `docs/security-review/10-remediation-status.md`:
the actor is asserted by the console, not proven by the person; the signer token is not mutual TLS.

## Backup and disaster recovery

Shares are backed up, encrypted to an offline recovery key split among officers, after every key change; a restore drill proves it. See [disaster-recovery.md](disaster-recovery.md). `MPC_ENV=production` refuses to start a node without backups.

## Provisioning existing workspaces
Keys are created on first signing. The gateway also backfills on start (serialised, resumable, retried with
backoff if the signer or nodes are down; `KEY_BACKFILL_ON_START=false` disables it) and on demand via
`POST /admin/custody/keys/backfill`, which returns `{created, already, failed:[{customerId, reason}]}`.
A workspace that had already signed with the old shared key keeps that history untouched; its new key's
row records the shared address (`legacy_signer_address`) so the two eras stay distinguishable.

## Broadcast
Set `ETHEREUM_RPC_URL` (and `ETHEREUM_NETWORK_NAME` for display). Without it the gateway signs only, and the
console says so rather than implying funds moved. With it:
- **Planning.** Nonce, chain id, gas and EIP-1559 fees are filled from the network. A transfer the balance
  can't cover (value plus maximum fee, less what earlier signed-but-unmined transfers already commit) is
  refused up front with `balance is X ETH; this transfer needs Y ETH including fees`, before anything is
  queued for approval.
- **Nonces.** Chosen at the last moment, under a per-address lock, so concurrent transfers never share one and a
  rejected or unsigned transfer never leaves a gap.
- **After signing.** The signed bytes are broadcast; a poller follows them to `confirmed`
  (`TX_CONFIRMATIONS`), `failed` (reverted, with the reason) or `stuck` (no receipt after
  `TX_STUCK_AFTER_MS`; never replaced automatically).
- **Broadcast failure** is recorded as `signed_not_broadcast` with the RPC error, not treated as success.
  **Rebroadcast** sends the same signed bytes (race-safe: one wins, and no second signature is made).
- Not handled: reorgs (a confirmed row is not re-checked), fee-bumping a stuck transaction, and a
  permanently-rejected signed transaction, which keeps its nonce until removed by an operator.

## What is not verified
- **AWS KMS** is tested against a local fake speaking KMS's protocol, not a real AWS account. `mpc-node seal-check -provider awskms` runs the
  same provider code against a real account in one command; it has not been run from this repo's test environment.
- **Separate hosts.** Nothing here can be proven on one machine: the mTLS, domain rule and preflight are
  exercised locally, but real network partitions, clock skew and per-host secrets are not.
- **The container image and example manifests** were not built or run (no container runtime here).
- **Domain labels** are self-declared.
- The seal key is held in process memory after start-up; a memory-reading attacker on a running node
  gets the shares of that node only.
- Resharing needs the new members to have pre-parameters ready (a CPU-heavy step); a node that has
  just been used may need a minute before it can take part in another.
